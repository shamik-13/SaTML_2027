# E12 dataset triage — a second dataset with genuine flow→campaign ground truth

**Date:** 2026-08-26 · **Scope:** half-day time-boxed triage, no bulk downloads · **Author:** automated triage for SaTML 2027 H2 (granularity–feasibility tradeoff)

**Question.** LSPR23 has no flow→campaign ground truth; our "episodes" are a heuristic `(SrcIP, DstIP, time-bucket)` key. Reviewer objection E12 asks whether the granularity tradeoff is an artefact of that heuristic or of LSPR23. Is there a **second, public network-traffic dataset carrying a real, dataset-provided flow/event → campaign/scenario/incident *instance* identifier**, with complete negatives and recoverable chronological order?

---

## 1. Verdict

# FAIL

**No public network-traffic dataset satisfying the required property exists as of August 2026.**

Across ~40 datasets examined and two independent catalogues covering 89 and 62 datasets respectively, **not one** ships a per-flow campaign/scenario/incident *instance* identifier that (a) originates from real operational ground truth rather than a host+time-window heuristic, (b) comes with trustworthy negatives, and (c) has enough distinct campaigns to support an online multiple-testing procedure. The field labels attack **classes** (`DoS`, `T1059`), not campaign **instances**; where instance-like structure exists, it is degenerate with the capture file or the network segment, which is precisely the grouping our heuristic already encodes.

Three near-misses were pursued to primary-source or raw-data level and each fails on a specific numbered rule:

- **CasinoLimit** (RAID 2025) — 114 played CTF instances looked like the best shot. I extracted the actual label schema from the Zenodo release: labels are `{id, auditd_events, technique}` where `technique` is a **MITRE ATT&CK technique string** — an attack class, not a campaign instance. Fails the required property outright, plus rules **2** and **5**.
- **GAMBiT** (2024–25 human-subjects red-team range) — 61 genuine operator-run operations, but **no per-flow labels of any kind** (raw PCAP + Suricata only) and each operator runs in an isolated clone. Rules **1**, **2**, **5**.
- **GUIDE / Microsoft Security Incident Prediction** — ~1M incident IDs at real scale, but `IncidentId` is produced by **Defender XDR's proprietary entity+time-window correlation engine**, i.e. a machine version of the very heuristic under test; timestamps are deliberately noised; no benign baseline. Rules **5**, **3**, **2**.

**One watch-item, not currently actionable.** **LMDG / LMTrace** (arXiv 2508.02942) has the only genuinely non-heuristic labelling method I found — "Process Tree Labeling", which traces Caldera agent PIDs through a process forest and stamps every host log and Windows Filtering Platform network event in that tree with attack scenario + version + step. That is provenance-derived attribution, exactly the right mechanism. **But the data does not exist publicly:** I checked the GitHub API — `WASPLab/LMTrace` is size 0, `"This repository is empty"`, last pushed 2025-02-09 (~18 months stale). It also has only 7 scenarios (35 executions), which is borderline on rule **4**. Cheap decisive check if wanted later: email the authors and ask (i) whether the release schema carries a stable per-execution instance key or only scenario+step, (ii) whether the 900 GB PCAP will be published. Cost: one email. Do not plan the extension around it.

**Recommendation.** Do not spend the 3–5 days. Print the paragraph in §5 as the answer to E12, and defend H2 on LSPR23 with the internal robustness evidence already generated (grouping-key sensitivity, `t26_H4_grouping.py`), reframing the episode key honestly as a *design choice with a measured sensitivity envelope* rather than an approximation to a ground truth that no public dataset provides.

### Bonus finding: our own dataset family is closed too

Two checks worth recording, both done against raw artefacts:

- **LSPR24 exists** (Zenodo 14900873, **CC0**, 20M flows, 31.6 h, 8 GB, scriptable) and was the strongest "sibling dataset" lead. I range-read the parquet footer and dumped the schema: labels are `Label`, `Label_src`, `Label_dst` (binary) plus Suricata `Category`/`SigID revision`/`Severity`/`Anomaly_event` (detector categories) and `Segment_*`/`Expoid_*` (host/segment). **No campaign column.** Confirmed by direct inspection, not inference.
- **LSPR24's `attack_narratives.json` is an empty shell.** 529 records, 492 attack narratives — but **0/529 have a real submitted step time, 0/529 contain an IP in `Content`, 0/529 have non-empty `Segments`**. LSPR24 is *worse* than LSPR23 for campaign reconstruction: even the manual path is unavailable.
- **LSPR23's narratives are richer but still insufficient.** 288 records (255 attack narratives); 155/288 carry ≥1 real `Steps_submitted_time`, but only **86/288 contain any IP** and only **45 distinct IPs** appear across all narrative content. `Steps_submitted_time` is when the Red Team *submitted its report*, not when the attack ran. Any flow→narrative join is therefore `(victim IP, approximate time window)` — **the same host+time heuristic we are trying to validate** (rules 1 and 5). This is a useful, honest sentence for the paper: we checked, and our own dataset's RT reporting cannot yield independent campaign ground truth.

## 4. What was searched

Four blind-to-each-other angles were run (three as parallel agents), then the top candidates were driven to primary sources and, where possible, to the raw bytes.

**Angle A — APT / multi-stage / kill-chain / red-team (run directly).** Queries: `multi-stage attack dataset network flows with attack scenario campaign labels per flow`; `APT dataset network traffic "campaign ID" OR "scenario ID" ground truth labeled flows`; `"kill chain" labeled network flow dataset attack stage labels per flow public`; `DARPA OpTC dataset red team ground truth per-event labels network flows`; `Unraveled dataset multi-stage attack campaign labels network traffic APT`; `CICAPT-IIoT SCVIC-APT-2021 DAPT2020 dataset campaign identifier per flow labels`; `dataset network traffic labeled with MITRE Caldera operation ID per flow ground truth attack automation logs`; `network dataset "attack instance" OR "attack session id" OR "episode id" label per flow`; `cyber range dataset "operation id" OR "run id" per flow red team emulation labeled 2025 2026`; `CTU-13 Stratosphere scenario labeled botnet dataset`.

## 5. Paragraph for the paper (answer to reviewer objection E12)

> Our episode key is a design choice, not an approximation to a ground truth we could have used instead: **no public network-traffic dataset provides genuine flow→campaign ground truth together with usable negatives.** We surveyed the field as of August 2026, including the two most complete catalogues available — a systematic review of 89 public NIDS datasets [arXiv:2502.06688] and the continuously-maintained COMIDDS survey of 62 datasets — and examined roughly forty candidates directly. Public datasets label attack *classes* (`DoS`, `PortScan`, ATT&CK techniques), not campaign *instances*. Where instance-like structure does exist, it fails in one of four ways. (i) It is a machine-produced correlation over the same host and time-window features we are testing: GUIDE's `IncidentId` is emitted by Defender XDR's proprietary entity+time correlation engine, and its timestamps are deliberately perturbed. (ii) It is degenerate with the capture file: PWNJUTSU (22 operators), GAMBiT (61 operators) and CasinoLimit (114 CTF instances) each isolate one operator per environment, so "campaign" is recoverable trivially by capture identity and campaigns are never interleaved — the attribution problem we study does not arise. (iii) Ground truth is prose requiring manual reconstruction from attack timetables — DARPA OpTC ships its red-team ground truth as a PDF; Cyber Czech ships a schedule spreadsheet and reserved attacker IP ranges; AIT-ADS labels alerts "based on their occurrence times". (iv) Negatives are absent or untrustworthy: honeypot corpora and CTF captures contain no benign traffic at all, and CTU-13's "background" class is explicitly unverified. We inspected the closest candidate, CasinoLimit [RAID 2025], down to its released label schema and found each label to be `{id, auditd_events, technique}` — a MITRE ATT&CK technique string, an attack class rather than a campaign instance — with attack labels present in only 114 of 140 instances and covering 6.4% of flows in the best-labelled instance we sampled. We also verified that the sibling exercise dataset LSPR24 carries only binary `Label`/`Label_src`/`Label_dst` columns with no campaign field, and that its released attack narratives contain no execution timestamps, target addresses, or segments (0/529 on each), making even a heuristic reconstruction impossible; LSPR23's own narratives carry submitted times for 155/288 records but addresses for only 86, so joining them to flows would itself require a host-and-time-window match — the very heuristic under scrutiny. We therefore evaluate the granularity–feasibility tradeoff on LSPR23 with an explicit sensitivity analysis over the episode key rather than against a campaign ground truth that does not exist publicly, and we note that the one dataset whose labelling method would suffice — LMDG's process-tree attribution from attack-orchestration agent PIDs [arXiv:2508.02942] — has not released its data (its repository remains empty as of August 2026) and spans only seven scenarios.
